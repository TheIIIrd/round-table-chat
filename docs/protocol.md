# Протокол

Что именно едет по проводу. Нужно, если вы собираетесь менять формат, писать
второй клиент или разбираться, почему два узла не понимают друг друга.

Текущая версия: **`p2pchat/2`**.

## Слои

```
приложение   текст, файлы, игры           mesh.py, envelope.py, files.py
соединения   кого пускать, куда звонить   network.py
сессия       хендшейк, ротация, привязка  session.py
транспорт    кадры, TCP                   framing.py, tcp.py
```

Слои не заглядывают друг другу внутрь. Сессия ничего не знает о TCP — ей
достаточно `Link` с методами «отправить кадр» и «получить кадр»; поэтому
добавление UDP или Tor не потребует правок в криптослое. Приложение не знает о
соединениях: оно получает байты и отдаёт байты.

## Кадры

```
uint32 длина (big-endian) | тело
```

Предел длины — 65 536 байт, и он проверяется **до** чтения тела: иначе четыре
байта от кого угодно заставят выделить четыре гигабайта. Кадр нулевой длины
отвергается.

## Хендшейк

`Noise_XX_25519_ChaChaPoly_BLAKE2s`, три сообщения:

```
-> e                 32 байта
<- e, ee, s, es      96 байт
-> s, se             69 байт + полезная нагрузка
```

Prologue: `p2pchat/2|<режим>|<идентификатор группы>`, где режим — `mesh` или
`direct`, идентификатор группы — 16 байт BLAKE2b от отсортированных публичных
ключей (в режиме `direct` пусто).

В полезной нагрузке третьего сообщения едет ник отправителя — он используется
только в режиме один на один и доверия не заслуживает: в групповом режиме ник
берётся из ростера.

После хендшейка обе стороны получают одинаковый handshake hash. Из него
выводится SAS: шесть групп по пять цифр, персонализация `p2pchat-sas-v1`.

## Транспорт после хендшейка

```
тип(1) | AEAD-шифротекст
```

Associated data: `тип(1) | счётчик отправителя(8, big-endian)`. Nonce — 96 бит:
32 нулевых, затем счётчик little-endian, как требует спецификация Noise.

Типы кадров сессии:

| Код | Что                                              |
|-----|--------------------------------------------------|
| 1   | данные приложения                                |
| 2   | начало ротации ключей (эфемерный публичный ключ) |
| 3   | подтверждение ротации (эфемерный публичный ключ) |
| 4   | просьба провести ротацию                         |

## Ротация ключей

Каждые 1000 сообщений или 900 секунд. Инициирует **только та сторона, что
начинала хендшейк** — иначе одновременный запуск с двух сторон дал бы два
разных набора ключей. Второй стороне остаётся послать просьбу (тип 4).

```
A -> REKEY_INIT (старым ключом), отправка данных приостановлена
B -> REKEY_ACK  (ещё старым), затем B переключается
A    получает ACK, переключается, возобновляет отправку
```

Порядок опирается на упорядоченность канала: данные, отправленные B сразу после
переключения, придут строго после ACK, поэтому A к этому моменту уже с новым
ключом. **На UDP это перестанет работать**, и будущий ARQ придётся строить с
учётом эпох ключей.

Новые ключи выводятся так: `ck, k1, k2 = HKDF(ck, DH(e_a, e_b), 3)`, где `ck` —
цепочка, унаследованная от хендшейка. То есть каждая ротация криптографически
связана со всей историей соединения. Счётчики сбрасываются в ноль.

## Конверт приложения

```
тип(1) | время отправителя, мс (8, big-endian) | тело
```

Заголовок — 9 байт. Время передаётся только для показа: часы участников
расходятся, и доверять им в упорядочивании нельзя.

| Код | Тип               | Тело                         |
|-----|-------------------|------------------------------|
| 1   | текст             | UTF-8                        |
| 2   | присутствие       | ник                          |
| 3   | предложение файла | id(16) размер(8) хеш(32) имя |
| 4   | приём файла       | id(16)                       |
| 5   | отказ от файла    | id(16)                       |
| 6   | кусок файла       | id(16) номер(4) данные       |
| 7   | конец файла       | id(16)                       |
| 8   | мой порт          | порт(2)                      |

Здесь были часы Лампорта. Они честно считались и ехали в каждом сообщении — и
нигде не использовались: получатель показывал реплики в порядке прихода. Поле,
которое никто не читает, хуже отсутствующего: оно создаёт впечатление, что
причинный порядок обеспечен. Настоящий межпировой порядок потребовал бы буфера
переупорядочивания и задержки.

## Передача файлов

Куски по 32 КиБ, предел файла — 64 МиБ, проверяется с обеих сторон. Хеш —
BLAKE2b-256 по всему файлу, считается в отдельном потоке, чтобы не морозить чат.
Приём идёт во временный файл `.<id>.part`; он переименовывается в настоящее имя
только после проверки хеша, поэтому недоделанный файл не появляется в каталоге.

Каждые 16 кусков делается короткая пауза — иначе поток кусков занимает канал с
этим участником целиком и переписка с ним замирает до конца передачи.

Ограничения: не больше трёх висящих предложений в каждую сторону на участника,
предложение живёт 5 минут, принятая передача без движения — 2 минуты.

## Согласованность величин

Некоторые числа связаны между собой, и правка одного без другого ломает работу
не при запуске, а посреди дела. На каждую такую связь есть тест.

| Связь                                        | Почему                                                                                           |
|----------------------------------------------|--------------------------------------------------------------------------------------------------|
| таймаут отправки > таймаута ротации          | ротация запускается внутри отправки; иначе исправного пира отключит посреди штатной смены ключей |
| кусок + заголовки ≤ полезной нагрузки сессии | иначе «сообщение длиннее допустимого» во время передачи                                          |
| версия протокола ↔ длина заголовка конверта  | иначе клиенты разных версий читают друг друга со сдвигом                                         |

## Как менять формат

**Любое** изменение того, что едет по проводу, требует поднять
`PROTOCOL_VERSION`. Версия входит в prologue, поэтому расхождение ломает
хендшейк громко и сразу. Без подъёма два клиента успешно соединятся и начнут
читать друг друга со сдвигом: файл придёт битым, текст превратится в мусор, а
искать причину придётся часами.

Тест `test_wire_format_change_requires_version_bump` падает при изменении длины
заголовка конверта и напоминает об этом. Обратной совместимости в протоколе нет
и не планируется: у группы из нескольких человек проще обновиться всем.

## Обнаружение в локальной сети

UDP-мультикаст `239.255.77.33:45333`, бикон каждые 2 секунды, TTL = 1.

```
"P2PB1" | длина id группы(1) | id группы | публичный ключ(32) | порт(2) | длина ника(1) | ник
```

Бикон не подписан намеренно: обнаружение не участвует в аутентификации, ключи
закреплены ростером, и подложный адрес даёт только неудачную попытку
соединиться. Подписывать подсказку, которую и так проверяет следующий шаг,
значило бы усложнять код без выигрыша.

## Приглашения

```
p2pchat:<base32>          участник
p2pchat-group:<base32>    весь ростер, сжатый gzip
```

Внутри: магия(4), версия(1), полезная нагрузка, контрольная сумма(4) от
BLAKE2s. Base32 выбран сознательно: его алфавит не содержит нуля, единицы и
восьмёрки, поэтому строку можно продиктовать голосом.

Разбор требует **каноничной** записи: в base32 последний символ несёт
неиспользуемые биты, и несколько разных строк декодируются в одни и те же
байты. Опечатка ровно в этом месте прошла бы мимо контрольной суммы.
