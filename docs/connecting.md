# Подключение

Главный документ проекта: всё, что касается «как нам увидеть друг друга».

Прежде чем разбирать сценарии, стоит понять одну вещь, из которой следует
остальное.

## Что нужно для соединения

Участнику нужны две разные вещи, и путать их вредно.

**Ключ** отвечает на вопрос «кто это». Он фиксируется в ростере, входит в
идентификатор группы и проверяется на каждом хендшейке. Ключ — это личность.

**Адрес** отвечает на вопрос «куда стучаться». Это подсказка, и только. Неверный
адрес приводит ровно к одному последствию — неудачной попытке соединиться. Из
этого следует важное практическое послабление: **адреса можно узнавать любым
удобным способом**, включая недоверенные, потому что аутентификация всё равно
опирается на ключ.

Адрес берётся из трёх источников, по убыванию свежести:

1. бикон обнаружения в локальной сети;
2. последний адрес, по которому соединение действительно получилось
   (`~/.p2pchat/known_peers.json`);
3. адрес из ростера.

Отсюда следствие, которое экономит нервы: **адрес в ростере важен только для
первого соединения.** Дальше он запоминается сам, и смена IP у собеседника
перестаёт требовать, чтобы все переписывали файл.

## Кто кому звонит

Соединение устанавливает тот, чей публичный ключ **меньше**. Правило одинаково
считается у обеих сторон, поэтому договариваться не нужно и двух сессий на пару
не возникает. Исключение: участник без своего адреса (`--listen none`) звонит
сам, потому что до него дозвониться некуда.

Практический вывод: если у вас есть хотя бы один участник с рабочим адресом,
остальные могут сидеть за NAT без всякой настройки — они дозвонятся сами. Но
между собой два «безадресных» участника соединиться не смогут.

# Сценарий 1. Все в одной локальной сети

Самый простой случай: ничего настраивать не нужно, адреса в ростере не
обязательны.

```bash
python -m p2pchat chat --listen 0.0.0.0:9333 --discover lan
```

Участники находят друг друга UDP-биконом в мультикаст-группе `239.255.77.33`
порт `45333`, каждые две секунды. TTL бикона равен единице — за пределы своего
сегмента сети он не уходит.

Бикон не подписан, и это осознанно: обнаружение не участвует в аутентификации.
Ключи зафиксированы в ростере, поэтому подложный адрес даёт только неудачную
попытку соединиться. Взамен в пределах сегмента видно, что участник с таким-то
ключом здесь присутствует — поэтому это флаг, а не поведение по умолчанию.

Ростер всё равно нужен: он определяет состав группы. Просто адреса в нём можно
не указывать.

# Сценарий 2. Все в интернете с доступными адресами

Каждый участник указывает в ростере свой внешний адрес и пробрасывает порт.

```bash
python -m p2pchat chat --listen 0.0.0.0:9333
```

Ростер:

```json
{
  "name": "друзья",
  "members": [
    {"nick": "alice", "key": "271d…", "address": "203.0.113.10:9333"},
    {"nick": "bob",   "key": "a8ee…", "address": "198.51.100.7:9333"}
  ]
}
```

На роутере: проброс внешнего порта `9333` на порт `9333` вашей машины, протокол
TCP. Проверить снаружи можно любым сервисом проверки открытых портов или с
другой машины: `nc -vz 203.0.113.10 9333`.

**Слушайте на `0.0.0.0`, а не на конкретном интерфейсе** — иначе соединение
придёт не на тот адрес и не будет принято.

# Сценарий 3. Смешанный: часть за одним NAT

Самый частый реальный случай и единственный с подвохом. Пусть alice и бот dice
сидят на одной машине, а bob и carol — где-то ещё.

Ростер один на всех, значит адрес участника в нём один — внешний. И вот
неочевидность: **двое за одним NAT по внешнему адресу друг друга обычно не
видят.** Пакет уходит на роутер и возвращается обратно, только если тот умеет
hairpin NAT, а умеют не все. Alice и dice будут прекрасно общаться с bob и
carol и при этом не видеть друг друга через комнату.

Три способа, по убыванию удобства:

**1. Обнаружение в локальной сети.** Работает и через loopback:

```bash
python -m p2pchat chat --home ~/.p2pchat/alice --listen 0.0.0.0:9333 --discover lan
python -m p2pchat bot  --home ~/.p2pchat/dice  --listen 0.0.0.0:9334 --discover lan
```

Проверено: участники находят друг друга, даже когда адрес в ростере указывает
на внешний IP, который изнутри не отвечает.

**2. Ручное подключение один раз.** В чате:

```
/connect 127.0.0.1:9334
```

Адрес запомнится в `known_peers.json` и дальше будет использоваться сам.

**3. Роутер с hairpin NAT** — если повезло, ничего делать не нужно.

**Не забудьте:** двум программам на одной машине нужны **два разных внешних
порта и два проброса**. Один проброс на двоих не работает.

# Сценарий 4. Разговор один на один без ростера

Когда группа не нужна:

```bash
# Тот, до кого дозваниваются
python -m p2pchat chat --listen 0.0.0.0:9333

# Тот, кто дозванивается
python -m p2pchat chat --direct 198.51.100.7:9333
```

Здесь нет ростера, поэтому нет и закреплённых ключей. Работает TOFU: первый
ключ запоминается, и при следующем соединении под тем же ником другой ключ
будет отвергнут с предупреждением. Ник берётся из полезной нагрузки хендшейка,
то есть его выбирает сам собеседник — доверять ему нельзя, доверять можно
только сверенному отпечатку.

# Сценарий 5. Ручное подключение

```
/connect host:port
```

Нужно, когда: адрес в ростере устарел, участник за одним с вами NAT, или вы
хотите соединиться до того, как сработает автоматический дозвон.

Автоматический дозвон повторяется с растущей паузой: от четверти секунды до
двух, пока кого-то не хватает, и раз в пять секунд, когда все собрались.

# Сценарий 6. Динамические адреса

Ничего настраивать не нужно, всё работает само:

- при успешном соединении адрес запоминается в `known_peers.json`;
- сразу после установки соединения каждая сторона сообщает собеседнику свой
  порт **внутри уже зашифрованного канала**; хост берётся из фактического
  сокета, потому что свой внешний адрес узел обычно не знает, а собеседник его
  видит.

Итог: тот, кто соединился с вами хотя бы раз, переживёт смену вашего IP, если
только вы оба не сменили адрес одновременно. В последнем случае поможет
`/connect` или обновление ростера.

# Сценарий 7. Несколько личностей на одной машине

Для стенда, для бота рядом с человеком, для проверки. Каждой личности нужно:

| Что                   | Зачем                                                    |
|-----------------------|----------------------------------------------------------|
| свой `--home`         | там лежат ключ, ростер, список известных пиров, загрузки |
| свой ключ             | `p2pchat --home <каталог> keygen`                        |
| свой порт             | `--listen 127.0.0.1:<порт>`                              |
| своя запись в ростере | со своим ключом и адресом                                |

Готовый стенд из трёх человек и бота:

```bash
python tools/local_testbed.py --reset
python tools/local_testbed.py --tmux          # сразу в панелях tmux
python tools/local_testbed.py --users петя,вася --no-bot
```

Скрипт создаёт ключи, раскладывает одинаковый ростер и печатает команды
запуска. Пассфраза у стенда одна и известная — это допустимо для песочницы на
localhost и больше нигде.

Группа собирается не мгновенно: расшифровка каждого ключа занимает около двух
секунд (Argon2id, 256 МиБ), а четыре клиента, запущенные разом, делят один
процессор. Дождитесь, пока `/peers` покажет всех.

## Обмен ключами: три способа

**Приглашение одной строкой** — основной путь:

```bash
python -m p2pchat invite --address 203.0.113.10:9333
# p2pchat:KAZFASIBHHWPYKLCKHX74IFFXIJZHAMYSRZB6QFUKNEPH25FMMN6S23WN5MAAJDV…
```

Принять: `p2pchat roster add-invite p2pchat:KAZ…`

**Приглашение всей группы** — когда состав собран, кто-то один раздаёт его
целиком:

```bash
python -m p2pchat invite --group
python -m p2pchat roster add-invite p2pchat-group:KAZ…
```

**Вручную**, если приглашения по каким-то причинам не подходят:

```bash
python -m p2pchat roster add bob a8ee76… --address 198.51.100.7:9333
```

Во всех трёх случаях остаётся обязательный шаг: **сверить отпечаток голосом**.
Приглашение содержит публичный ключ, и если оно шло через канал, который
контролирует противник, ключ подменяется. Подробнее — в
[security.md](security.md).

## Идентификатор группы

Считается как BLAKE2b от отсортированных публичных ключей участников и входит в
prologue хендшейка. Следствия:

- у всех должен быть **одинаковый** ростер, иначе соединения не будет;
- добавление или удаление участника создаёт **новую** группу;
- расхождение обнаруживается при соединении, а не проявляется странностями
  через час.

Посмотреть свой: `python -m p2pchat roster show`

## Порты и брандмауэр

| Что                     | Протокол | Куда                                  |
|-------------------------|----------|---------------------------------------|
| Основной порт участника | TCP      | пробросить снаружи, по умолчанию 9333 |
| Порт бота               | TCP      | отдельный проброс, по умолчанию 9334  |
| Обнаружение в сети      | UDP      | 45333, только внутри локальной сети   |

Порт обнаружения наружу пробрасывать не нужно и не следует.

## Чего пока нет

**UDP hole punching.** Если ни у кого в группе нет доступного адреса, соединения
не будет: нужен хотя бы один участник, до которого можно дозвониться. Обход NAT
через STUN и rendezvous — следующий этап.

**Tor.** Onion-адрес снял бы и проброс портов, и динамические адреса, и
метаданные разом; в коде это была бы ещё одна реализация `Link`, без изменений в
остальном. Пока не сделано.
